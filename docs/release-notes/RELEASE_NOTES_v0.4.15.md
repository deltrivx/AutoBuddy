两个改动：一个是静默丢配置的缺陷，一个是新增的一键恢复。

## 一、修复：「设为首选」会清空账号白名单

账号卡片上有两个按钮，语义不同但共用同一个保存接口：

- **「设为首选」** —— 只改「用哪个账号」，提交 `mode` 与 `manualAccountId`；
- **「启用 / 停用」** —— 改「哪些账号参与轮询」，提交账号白名单。

缺陷出在服务端读取入参的方式：缺字段时取默认值。于是「设为首选」没带
`enabledAccountIds`，被读成空数组并**覆盖落盘** —— 白名单在一次「设为首选」后
整份丢失。

这个缺陷有两点让它很难被发现：

| | |
| :--- | :--- |
| **现场没有异常** | 空数组在业务上表示「全部启用」，丢失之后账号看起来全都还在，界面毫无异样 |
| **重启也恢复不了** | 文件在设置的那一刻就已经被改写，重启或重建容器都救不回来 |

所以它表现为「我设了首选账号，过一阵发现没生效」，而查日志、查持久化目录
都看不出问题 —— 因为问题早在设置时就发生了。

现在服务端改成**以已保存的配置为底，只覆盖调用方明确提交的字段**。
前端也补上 `enabledAccountIds`，两层都不再依赖「缺省即重置」这种危险语义。

顺带修了一处：切到手动分配但没指名账号时，过去会直接报错，于是「只想改白名单」
的请求会因为历史配置里没有首选账号而失败。现在这种情况退回自动分配，
不影响白名单的更新。

## 二、新增：模型一键恢复

账号卡片的「可用模型」标题行新增一个按钮：

```
可用模型 · 12   已禁用 3   巡检 2   [ 全部恢复 5 ]
```

点一次把该账号被禁用的模型**全部**放回轮询。之前只能逐个点模型标签，
巡检误禁一批、或手动关掉几个后想一次放开时，点起来很碎。

- 按钮**只在确实有禁用项时出现**，文案带上要恢复的数量，点了有结果提示。
- 恢复范围**含手动禁用** —— 诉求是「让这些模型重新参与调用」，当初是谁禁的不重要。
  需要保留人工决策的场景走接口的 `scope=auto` 用法：只放回巡检写的那些。
- 恢复会改变路由行为，落盘前自动留底，便于回溯。

## 三、修复：恢复接口的字段形状

`disabledModels` 此前在恢复接口里返回集合、在禁用切换接口里返回列表 ——
同一字段两种形状，调用方要写两套判空。现在统一为排序后的数组。

## 不改变的行为

- 「启用 / 停用」按钮的语义与账号池白名单的行为不变。
- 模型禁用的来源标记（手动 / 巡检）机制不变，巡检仍不会自动放回手动禁用的模型。
- 单个模型标签的点按启停照旧。
