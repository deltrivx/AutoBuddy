# AutoBuddy v0.9.7

> 修正认证凭据语义为「环境变量在场即覆盖、不在场则保留」。

## 问题

v0.9.6 对认证凭据的处理改错了方向。

v0.9.6 为了解决「取消环境变量后原密码登不上」，把逻辑改成
**环境变量仅在首次建账号时生效**，并以 `auth.bootstrap_password`
标记判断「环境变量是否变化」——只有值**确实变了**才覆盖。

这带来一个新的后果：当环境变量**在场且值未变**时不再覆盖，
于是用户在面板改过的密码反而存活下来，**环境变量失去了权威性**。

## 检测

用隔离的临时数据库逐条实测（凭据用占位值，不触碰任何生产数据）：

| 规则 | 期望行为 | v0.9.6 实测 | 判定 |
| :--- | :--- | :--- | :--- |
| A. 有环境变量 | 写入数据库 | ✅ | 符合 |
| C. 最初无环境变量 | `admin` / `password` | ✅ | 符合 |
| D. 用户自行修改 | 写入数据库 | ✅ | 符合 |
| B. 移除环境变量 | 保留最新写入值 | ✅ | 符合 |
| **E. 后续再设环境变量** | **继续覆盖写入** | **PANEL_B 仍生效、ENV_A 失效** | **❌ 违反** |

复现路径：环境变量 `ENV_A` 启动 → 面板改密码为 `PANEL_B` →
重启且环境变量仍为 `ENV_A` → 结果 `PANEL_B` 仍可登录、环境变量失效。

## 语义界定

凭据规则明确为五条：

| 规则 | 行为 |
| :--- | :--- |
| A. 有环境变量 | 写入数据库（环境变量权威） |
| B. 环境变量移除 | 数据库保留最后一次写入的值，不回落默认值 |
| C. 最初无环境变量 | 默认 `admin` / `password` |
| D. 用户自行修改 | 写入数据库 |
| E. 后续再设环境变量 | 继续覆盖写入 |

五条可收敛为实现上的两条规则：

1. **环境变量在场 → 无条件覆盖**（对应 A / E）
2. **环境变量不在场 → 一行都不动**（对应 B / D，用户改的成果得以保留）

这样既保证环境变量始终是权威源，又保证移除环境变量后
数据库保留最新值、不会回落成默认 `password`。

## 修复

- `init_db()` 中的账号同步逻辑按上述两条规则重写；
- 删除 v0.9.6 引入、如今已无引用的引导标记机制
  （`auth.bootstrap_password` 常量与 `_init_read_bootstrap` /
  `_init_write_bootstrap` 两个辅助函数）。

## 验证

隔离临时库按五条规则逐条实测：

```
A 有环境变量 → 写入数据库            ✅
D 用户自行修改 → 写入数据库           ✅
E 后续再设环境变量 → 继续覆盖         ✅（ENV_A 重新生效、PANEL_B 失效）
E 环境变量换新值 → 同样覆盖           ✅（ENV_C 生效）
B 移除环境变量 → 保留最后写入 ENV_C   ✅（未回落默认 password）
C 最初无环境变量 → admin/password     ✅
```

五条规则全部符合。

## 升级说明

重建容器即可，`/data` 数据不受影响。

- 无新增或删除环境变量；
- 无数据库结构变更；
- 若模板中**保留**了 `AUTH_USERNAME` / `AUTH_PASSWORD`，
  每次启动都会以环境变量为准覆盖（这是预期行为，规则 A / E）；
- 若希望使用自己在面板设置的密码，将这两个环境变量从模板中移除即可
  （规则 B / D）。
