# AutoBuddy v0.9.6

> 修正每日任务完成度统计、修复移动端竖屏状态图标、修正认证凭据被环境变量覆盖。

## 1. 每日任务完成度统计修正

### 问题

每日任务页「任务记录」中，除「批量接受任务」外，其余所有任务项的完成度
长期显示 `成功 0/N`。

### 根因

任务结果判定只认三个成功信号：`✅`、`成功`、`+ `（加号**带空格**）。
而上游脚本输出的真实成功文案几乎都不在其中：

| 真实成功文案 | 原判定 | 应为 |
| :--- | :--- | :--- |
| `📦盲盒: 暗影喵(SR)` | info ❌ | success |
| `🎁领奖[first_buddy]: +300积分+8能量` | info ❌ | success（`+300` 无空格） |
| `Buddy_App_QQ: buddyapp 五连 OK` | info ❌ | success |
| `🐾旅行: 旅行中，约37分钟后到达` | info ❌ | success |

只有 `📋批量接受 19 项 → 成功 1 / 未登记 18` 恰好含「成功」二字，
所以它是唯一有完成度的任务 —— 与用户观察到的现象完全吻合。

实测数据库分布印证了这一点：

```
accept_tasks  7 条  全为 success
blindbox     18 条  全为 info
buddy        84 条  全为 info
checkin      18 条  全为 already
claim        69 条  全为 info
lottery      36 条  全为 info
travel       18 条  全为 info
```

### 修复

判定逻辑改为**先排除再肯定**：

1. **否定信号优先** —— `能量不足`、`无次数`、`无需抽`、`跳过`、`余额=0`、
   `✗`、`not_accepted`、`not completed`、`无法登记` 等，命中即不算成功；
2. 再依次判定 `failed` → `already` → `success`；
3. **成功信号按形态识别**：
   - 抽卡：`(喵|伙伴|卡)(SSR|SR|UR|R)` 稀有度
   - 奖励：`\+[1-9]\d*\s*(积分|能量|credits?|energy)` —— 正增量，`+0` 不算
   - 文案：`✅` / `成功` / `OK` / `五连 OK` / `获得` / `抽中` / `已到账` / `领取成功`
   - 旅行：`旅行中` / `约 N 分钟后到达` / `即将到达`

**边界处理**：

- `无法登记` 判为 **failed** —— 登记这个动作确实没做成；
- `not completed yet` 判为 **info**（待完成）—— 条件未满足，不是执行失败，
  不能因此把完成度抹黑。

已用 14 条真实日志样本做回归验证，全部符合预期。

## 2. 移动端竖屏状态图标与签到徽章不再消失

### 问题

移动端竖屏（≤560px）下，国内账号（cn）的旅行飞机图标与签到徽章不显示。

### 根因

窄屏时 `.wb-api-row` 切换为纵向布局（`flex-direction: column`），
而状态徽章容器是 `flex: 0 0 auto` 且 `white-space: nowrap` 不允许换行 ——
宽度不足时整组徽章被挤出可视区，或被祖先的 `overflow` 裁切，
表现为「图标不见了」。

### 修复

- 徽章容器改为 `flex: 0 1 auto`（可收缩）+ `flex-wrap: wrap` + 右对齐；
- 补窄屏专用样式：徽章允许换行（`white-space: normal`）、
  飞机图标 `flex-shrink: 0` 不收缩、SVG 尺寸统一为 12px。

## 3. 认证凭据不再被环境变量无条件覆盖

### 问题

用户反馈「取消环境变量后，原用户名和密码认证失败」。

### 根因

原逻辑只要检测到 `AUTH_PASSWORD` 就**每次启动都覆盖**数据库密码：

```python
if os.getenv("AUTH_PASSWORD") or ...:
    # 无条件 UPDATE users SET password_hash = ...
```

导致两个后果：

1. 用户在面板改过的密码，容器一重启就被打回环境变量值 —— 改了个寂寞；
2. 用户从模板里移除环境变量后，启动时 `env_pwd` 回落到默认 `"password"`，
   而 `users` 表里存的已是别的值，于是「正确的密码登不上」。

实测数据库（用 `sha256(pwd + salt)` 比对）印证：

| id | 用户名 | 环境变量密码匹配 | 实际来源 |
| :--- | :--- | :--- | :--- |
| 1 | admin | ✗ | 面板自设 |
| 3 | DeltrivX | **✓** | 被环境变量强同步 |

### 修复

语义改为：**环境变量仅在首次建立账号时生效**，之后它就是普通初始值，
与用户在面板设置的新密码完全等价 —— 谁最后改，谁生效，重启不再干预。

- 记录 `auth.bootstrap_password`（引导密码）到 `system_config`；
- 仅当环境变量密码与该标记**确实不同**时才同步（照顾用户主动改环境变量的场景）；
- 内容没变就绝不动数据库，面板改过的密码得以保留。

**连带修正**：读写引导标记时复用 `init_db` 自身的 cursor，
不再调用会另开连接的 `get_config` / `set_config` ——
否则在事务未提交时触发 `database is locked`。

### 验证

五个场景端到端实测：

| 场景 | 期望 | 结果 |
| :--- | :--- | :--- |
| A 首次带环境变量启动 | 环境变量密码可登录 | ✅ |
| B 面板改密码 | 新密码可登录 | ✅ |
| C 带**同样**环境变量重启 | 用户密码仍有效、旧密码不复活 | ✅ |
| D **取消环境变量后重启** | 用户密码仍可登录 | ✅ |
| E 主动更换环境变量密码 | 新环境变量密码生效 | ✅ |

## 升级说明

重建容器即可，`/data` 数据不受影响。

- 无新增或删除环境变量；
- 无数据库结构变更（新增的 `auth.bootstrap_password` 走既有 `system_config` 表）；
- 若此前因该问题无法登录，修复后**面板自设的密码会保留**，
  用面板密码登录即可；如确需重置，删除容器环境变量即可恢复默认凭据。
