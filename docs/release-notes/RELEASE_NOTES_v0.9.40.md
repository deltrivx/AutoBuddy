> 修复「近7日消耗和本月消耗比今日消耗还低」——累计值小于单日值，数学上不可能。

## 用户报告

> 积分统计，近7日消耗和本月消耗比今日消耗还低

这在数学上不可能：今日窗口必然包含在「近 7 日」与「本月」窗口内，累计值一定 >= 单日值。

## 根因（线上实测）

实测 `/api/credits/stats`：

| 字段 | 顶层 `summary`（全量 20 账号） | `officialUsage.summary`（前端实际采用） |
|---|---|---|
| `usageToday` | 5280.01 | 5280.01 |
| `usage7Days` | 19573.14 | **3597.49** ❌ |
| `usageThisMonth` | 21435.50 | **3819.01** ❌ |

`officialUsage` 这条采集通道只覆盖 **6 个账号**，顶层是全量 **20 个账号**，
所以它的**合计类**字段天然偏小。而官方前端优先采用 `officialUsage`
（`status=complete` 即视为可用），于是把全量累计值覆盖成了残缺值。

这是 2026-10-08 修复「今日消耗一直是 0」时留下的**半截尾巴**：
当时只对账了 `usageToday`，并在注释里假设「usage7Days / usageThisMonth 官方是有值的」。
实测证明该假设不成立 —— 凡是被覆盖的子集通道，它的合计类字段一律不可信。

## 修复

`_reconcile_official_usage()` 原本只校准「今日」。本版把 `usage7Days` / `usageThisMonth`
一并纳入同一套「以顶层为准」的对账逻辑。

另外加了一道**单调护栏**：即便两份数据仍然打架，也保证「近7日 >= 今日」且「本月 >= 今日」——
宁可保守，也不能向用户展示违反常识的数字。

> 注意：这里**不**强行断言「本月 >= 近7日」。月初前几天本月窗口可能短于 7 天，
> 那样断言反而会造出一个新的错误。

同时更新了那条误导性的旧注释，并把教训留在文件里：
「部分字段准」不等于「其余字段也准」，给外部数据源做对账时必须逐个字段验证。

## 测试

新增 `_test_credits_usage_monotonic.py`（15 项）。它不是字符串匹配，而是用 `ast`
从源码里抠出 `_reconcile_official_usage` 真实 `exec`，灌入复现缺陷的真实数据后断言输出：

1. 用户报告的真实数据 → 累计取到顶层全量值且满足单调；
2. 顶层累计缺失时不用残缺值覆盖、也不清零；
3. `officialUsage` 今日为 0（2026-10-08 原始缺陷场景）时 daily 兜底仍生效；
4. `officialUsage` 缺失 / 为空 / summary 为 None 时安全返回不崩溃。
