> 官方积分采集 9-24 起停更：账号明细（近7日/本月/按日图表）由网关实时数据整体接管。

## 用户报告（三个疑点，逐一实证）

> 今天积分 7162.85 是否真实（历史最高）？近7天和近一个月消耗就没变过。官方积分消耗 9-24 号开始停止，接口坏了还是什么原因？查看其他类似项目有没有同样问题，没有就参考其他类似项目进行修复。

### 疑点 ①：今日 7162.85 是否真实 —— 真实

独立核算（快照剩余差，不依赖面板口径）：23:07 时全 15 账号合计 **7823.46**，
全部账号的午夜基准都贴在 10-10 23:26（距午夜仅 0.55h，v0.9.41 的重归因生效）。
面板显示 7355.55（23:06 时点，比独立核算略低是因重归因把午夜前 0.55h 归还给了昨天）。
请求量交叉验证：当天 1991 次请求，量级吻合。**今日消耗创新高是真的**——
账号池已扩到 15~20 个、每日任务在跑、加上正常调用，日消耗上 7000+ 属正常水位。

### 疑点 ②：近7日/本月「没变过」—— 定位到 ou.accounts[]

网关自己的 summary 一直在滚动（25910 → 37561 → 38570），没变的是
**officialUsage.accounts[]**：每个账号的 daily 全部停在 `2026-08-25 → 2026-09-24`
（31 天窗口不滚动），usage7Days / usageThisMonth 是 9-24 的旧值——
而账号卡片和按日图表读的正是这份。v0.9.40 只校准了 ou.summary 三个数，
漏了 ou.accounts[]，这就是「没变过」的真因。

### 疑点 ③：官方 9-24 起停止 —— 接口没坏，是采集环节停了

直连引擎 `:57890/api/credits/stats` 返回 HTTP 200（17ms），顶层 summary 实时
（usageToday=8731.84）。坏的只是 officialUsage 这条采集支线：collectedAt
停在 2026-09-24（停更 18 天）。该环节在官方闭源二进制内，网关无法触发其重写。

## 参考项目调研结论

workbuddy2api-panel（2k stars）**根本不消费 officialUsage**——自建
`internal/usage.Recorder`（逐请求记录 + 窗口聚合 + 三种统计窗口）。
没有「同样问题」因为它压根不用那条数据链路。

## 修复：账号明细整体接管

参照 panel 的思路，网关侧全量接管 ou.accounts[]：

- 用**已完成重归因 + 滚动求和**的顶层实时账号替换 `ou.accounts[]`，
  并标记 `source: "gateway-realtime"`；
- `rangeEnd` 对齐到今天，不再挂着误导性的「数据截止 9-24」；
- freshness 文案区分接管状态：陈旧的只是官方原始采集那份，
  面板看到的数据是实时口径；
- 顶层 accounts 为空时不接管（保留官方原始数据）。

守恒性：ou 与顶层引用同一份数据，两栏数字天然一致，不会再打架。
