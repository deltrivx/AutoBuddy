修 v1.0.18 留底机制自身的两个 bug —— 同秒多次留底会互相覆盖丢内容，清理旧备份可能删掉更新鲜的那份。

**发布说明里最重要的一句**：v1.0.18 的安全门（32 个零鉴权路由补登录门）没有问题，这一版修的是**它自己带出来的留底代码**的三个坑。如果你已经升到 1.0.18，升这一版；如果还在 1.0.17，建议直接升 1.0.19。

---

## 修了什么

### 1. 同秒内多次留底会互相覆盖，中间几份内容全丢

原实现的同秒兜底后缀用的是 `-{pid}`。问题在于 **pid 在同进程内是定值** —— 同一次运行里，第 2 次、第 3 次、第 4 次留底全都写到同一个文件名上，后写的把前面的覆盖掉。

这不是理论问题。账号池最高频的写入来源是「刷新令牌」（一次刷新就落盘一次），而批量刷新令牌、导入整包账号都是在**同一秒内连续落盘**，必然命中这个坑。

实测（容器内、临时目录、不碰真实数据）：

```
第 1 次变更 → accounts.json.bak-20261022T031500Z     ✓
第 2 次变更 → accounts.json.bak-20261022T031500Z-1   ✓  （原实现：覆盖掉上面那份）
第 3 次变更 → accounts.json.bak-20261022T031500Z-1   ✗  （又覆盖第 2 份）
...
5 次连续变更 → 原实现只留下 2 份，中间 3 份内容全丢
修复后      → 5 份完整备份，一份不少
```

改为递增后缀 `-1` / `-2` / `-3` …

### 2. 清理旧备份时可能删掉更新鲜的那份

`_prune_accounts_backups()` 按**文件名字典序**排序来挑「最旧的删」。同秒产生的文件，带后缀的（`...Z-1`）和不带后缀的（`...Z`）字典序是乱的 —— `Z-1` 排在 `Z` 后面，但它们的 mtime 可能只差几毫秒，也可能反过来。

排序错了，删掉的就不是最旧的那份。改为按 **mtime** 排序。

### 3. 自建 / 测试环境下留底静默失败

`_backup_accounts()` 原先硬编码权威源路径（`/data/.wb-switch/accounts.json`）。在没挂载官方引擎数据目录的环境里（自建、测试），这个路径不存在，函数返回 None —— 不报错、不抛异常、也不留底。

最坏的情况是「以为留了备份，其实一个文件都没有」。改为对**实际参与写入的第一个目标**留底，与权威源路径是否存在解耦。

## 验证

容器内隔离验证（临时目录，全程未触碰真实账号数据）：

| 场景 | 结果 |
|------|------|
| 5 次连续变更 | 5 份完整备份（`v0` … `v4`），一条不丢 |
| 30 次连续写入 | 压到 20 份上限，删除的都是最旧的 |
| 原文件不存在 | 返回 None，不抛异常 |

回归测试 `_test_gateway_auth_gate.py` 补 3 项断言把这三个坑锁住（**61 项**）：同秒多次留底不得互相覆盖、清理必须按 mtime、无原文件不得抛异常。

全仓回归：**59 个测试文件全绿**。

## 升级

```bash
# Unraid 容器模板 AutoBuddy，镜像标签 ghcr.io/deltrivx/autobuddy:1.0.19
docker pull ghcr.io/deltrivx/autobuddy:1.0.19
php /usr/local/emhttp/plugins/dynamix.docker.manager/scripts/rebuild_container AutoBuddy
curl -s http://127.0.0.1:18091/health   # version 应为 1.0.19
```

账号数据不受影响 —— 留底只新增 `.bak-*` 文件，不修改 `accounts.json` 本身。
