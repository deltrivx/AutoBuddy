## 需求

v0.4.3 着手修复巡检把好模型成批误禁的问题，方向是对的，但只修完了其中一部分：
探测请求里仍然保留了一个带取值范围校验的可选参数，而上游对这个参数设有最小值。

结果是同一类故障换了个面孔又出现一次 —— 某几个账号名下的**全部**模型被整体判成不可用，
一轮下来又新增 44 项误禁；另外还有一类此前没被识别的情况：某个账号的上游凭据失效时，
该账号名下所有模型逐个被写进禁用清单，而真正需要做的只是重新登录。

v0.4.4 把这两件事一并收尾，并把「探测自己出问题」的几种情形与「模型真的坏了」
彻底分开 —— 前者一律不写配置。

---

## 一、修复：探测请求仍带了一个会被上游校验的参数

**症状**：开启巡检跑一轮，结果是「探测 200 个组合，可用 132、不可用 68」。
表面看比上一版的「可用 0」正常得多，但逐账号看就不对：

| 账号 | 探测结果 | 说明 |
| :--- | :--- | :--- |
| A / B / C | 大部分可用，3 个不可用 | 正常 |
| D / E / F / G | **11 个全部不可用** | 一个可用的都没有，不像真实情况 |

对这四个账号里的任意一个模型单独复测，得到的是上游的参数校验错误 ——
问题不在模型，而在这四个账号走了另一条上游线路，那条线路会校验这个参数的最小值。

**原因**：探测请求里带了「输出上限」参数，值为 1。这在其中一条线路上被接受，
在另一条线路上被回绝。同一个请求形态在不同线路上得到不同结果，
判定逻辑把回绝读成了「这个模型不可用」。

**修复**：探测请求不再携带任何**可选**且带取值范围校验的参数，
其形态与普通客户端请求完全一致。「少发一点」改为靠**读到流式响应的第一帧就断开**来实现，
代价比之前更低。

## 二、新增：探测被上游拒绝时不再写配置

修掉根因还不够。这类缺陷的后果特别重：它不报错、不提示，只是安静地把配置改坏，
而且要等用户自己发现。所以这一版把「探测侧的问题」与「模型的真问题」彻底分开：

| 探测结果 | 含义 | 是否写入禁用 |
| :--- | :--- | :--- |
| 正常返回 | 这条路通 | 否（若此前是巡检写入的禁用项，则放开） |
| 上游报出模型不可用 / 不存在 / 无权限 | 这条路真的不通 | **是** |
| 限流、超时、网络异常 | 暂时测不准 | 否 |
| 上游拒绝了探测请求的参数 | 探测本身有问题，对模型一无所知 | 否 |
| 整轮一个可用的都没有 | 探测机制整体失效 | 否，整轮作废并提示原因 |

其中「上游拒绝了探测请求的参数」是这一版新加的类别：逐条跳过，
若整轮都是这种情况则整轮作废，并把上游给出的错误码显示在面板上，
方便直接判断是不是探测形态又需要更新。

## 三、新增：账号凭据失效不再牵连模型

一个账号的上游凭据失效（最常见的是 token 过期）会让该账号名下**所有**模型一起失败。
此前这会逐条写成自动禁用 —— 一次过期就禁掉整个模型清单，而真正该做的是重新登录。

现在检测到整个账号都栽在鉴权上时会**整体跳过该账号**，不为它写入任何禁用项，
并在巡检面板上点名列出，提示重新登录：

- 被跳过的账号只是本轮没有结论，重新登录后下一轮即可恢复正常判定；
- 其余账号照常参与，互不影响。

这样处理的依据是：坏的是凭据，不是模型 —— 禁用模型清单解决不了登录问题，
反而会在重新登录后留下一堆需要逐个放开的误禁。

## 升级方式

```bash
docker pull ghcr.io/deltrivx/workbuddy-switch:v0.4.4
docker pull ghcr.io/deltrivx/workbuddy-switch:latest
```

- **Unraid**：走容器模板重建（在 Docker 页面选中该容器 → 编辑 → 应用），
  不要手工拼接 `docker run`。数据目录不变，账号与配置都不受影响。
- 若你的实例曾被旧版巡检写入过误禁项，数据目录里保留了改动前的策略备份，
  把它覆盖回策略文件、重启容器即可整份回退；之后跑一轮新版本巡检会重新得出正确结论。

## 不改变的行为

账号管理、自动签到、账号池调度（并行轮询 / 手动首选 / 请求级指定账号）、Token 统计、
模型别名路由、模型标签的手动禁用，以及巡检的开关、间隔、账号范围与自动启用设置 ——
**全部保持不变**。

「限流与超时一律跳过」「同一时刻只允许一轮巡检」「巡检不阻塞正常调用」
「自动启用只放开巡检自己写入的禁用项、手动禁用永不被放开」——
这些取舍继续沿用。
