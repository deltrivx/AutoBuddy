## 一、修复：卡片上的「已禁用」把巡检禁用也算进去了

账号卡片标题行右侧有两个徽标。「已禁用 N」原本统计的是**全部**被禁用的模型，
于是巡检自动禁用一个模型，这个数也跟着 +1 —— 它和旁边的「巡检 M」指向同一批模型，
能看出「有几个被禁了」，却看不出「哪几个是我自己关的」。

现在两个数字的口径**互不重叠**：

| 徽标 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 已禁用 N | 手动禁用 + 巡检禁用 | 只数**手动**禁用的 |
| 巡检 M | 其中有多少是巡检写的 | 只数**巡检**写的 |

**为什么会被数两遍**：「已禁用」原先是禁用项总数，「巡检 M」是其中的子集 ——
子集标注在表格里说得通，摆成两个并排的徽标就成了同一批模型数两遍。
现在改成两个互斥的计数，与标签本身的配色区分（灰色虚线 = 手动，琥珀色虚线 = 巡检）也对上了。

## 二、变更：巡检不再探测手动禁用的模型

手动禁用是明确的取舍，模型本身往往是好的（常见于「能跑但太贵」这类）。巡检此前会照常探测它们，
拿到「可用」的结论后再特意跳过 —— 结论用不上，请求却真实发了出去，也真实消耗了额度。

现在这类组合**整个不进入探测清单**：

- 省下的是真实的上游请求，所以一轮巡检的组合数会明显少于一页卡片的模型总数；
- 少掉的这部分会在巡检结果里单独说明（「手动禁用 N 项未探测」），而不是混进探测计数里 ——
  否则看起来就像「有些模型莫名没被检查」；
- 巡检**自己写入**的禁用项照常参与探测：模型恢复可用时，仍然会自动放开。

## 三、修复：巡检结果在重启后丢提示

巡检结果会存一份摘要，页面在进程重启后正是读这份摘要回显。摘要里有两项只在当轮存在、
重跑一轮也补不回来的内容 ——「凭据失效、本轮已跳过的账号」与被上游拒绝的探测错误码 ——
此前没有被存进去，于是重启之后这两个提示就再也不出现了。现在一并存入。

## 不改变的行为

手动禁用的写入与来源保护、模型可用性巡检的开关与判定规则（限流跳过、凭据失效整账号跳过、
整轮无有效信号作废）、账号池调度（并行轮询 / 手动首选 / 请求级指定账号）、模型别名路由 ——
**全部保持不变**。

对外提供的 OpenAI 兼容接口、请求与响应字段**没有任何增删**。
