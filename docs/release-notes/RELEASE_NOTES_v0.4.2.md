## 一、设置页新增「模型可用性巡检」

在设置页新增一个面板，四件事可调：

| 设置项 | 说明 |
| :--- | :--- |
| **自动巡检** | 总开关。开启后按间隔自动跑；关闭后不再自动动配置，但**已写入的禁用项继续生效**。 |
| **巡检间隔** | 两次巡检之间等待多久，最短 5 分钟。 |
| **巡检账号范围** | 不选 = 全部账号参与；也可以只勾选部分账号。 |
| **检测到可用时自动启用** | 开启则「恢复可用」会自动移出黑名单；关闭则只自动禁用、不自动放开。 |

另有一个「只探测用过的模型」开关，用于控制探测范围（见第三节）。

面板里还有 **「立即巡检」** 按钮：点一下立刻跑一轮，不改变上面的开关状态。
跑完会直接告诉你本轮结果 —— 探测了多少个组合、可用 / 不可用各多少、新增禁用与启用各几项。
上一次的变更明细也会留在面板上，方便回头对照。

## 二、判定标准：什么算「不可用」

探测只发一个极小的请求（1 个 token），**只看 HTTP 状态码，不看回答内容**。
目的是确认「这条路通不通」，不是「回答得好不好」，所以探测内容不会被记进用量统计。

判定刻意分成了三档，而不是简单的「成功 / 失败」：

| 结果 | 触发条件 | 处理方式 |
| :--- | :--- | :--- |
| **不可用** | `400` `401` `403` `404` `422` `500` `502` `503` `504` | **自动禁用** |
| **可用** | `200` 等正常状态 | 若开启了自动启用，则移出黑名单 |
| **跳过** | `429`（限流）、`408`、`425`、网络异常 / 超时 | **不改变任何配置** |

第三档是最重要的设计取舍。上游在高峰期限流是**常态**，
如果把它当成「不可用」，一轮巡检就能把所有好模型全部禁掉 —— 而且下一次巡检还会继续禁。
所以凡是「说不清是模型坏了还是此刻太挤」的情况，一律不动配置，宁可漏禁也不能误禁。

## 三、探测范围：默认只探「用过的模型」

一个账号可能对应几十个模型，全部探测会产生可观的上游调用量。
因此默认**只探测该账号实际调用过的模型**（依据网关已有的调用流水）；
账号还没有任何调用记录时，退回内置的基础模型清单，保证新账号也能被覆盖到。

关闭这个开关会探测全部已知模型 —— 覆盖更全，但组合数量会大很多，请谨慎使用。

## 四、自动禁用与手动禁用是同一份配置

自动巡检写入的，就是手动点标签写入的那一份策略，两者共用同一个存储：

- **关掉自动巡检后，之前自动写入的禁用项依然生效**，且可以在账号卡片上手动启用 / 重新禁用。
- 手动禁用的模型，巡检发现它可用时也会按「自动启用」开关的设定来决定是否放开。
- 策略仍然**只记「被禁用」的项**，未列出的一律视为可用，官方上新模型时天然可用，不需要迁移配置。

换句话说：巡检只是**替你按标签**，它没有自己独立的一套状态。

## 五、不会被巡检拖慢

巡检期间需要向上游发出多轮真实请求，这个过程**不会阻塞正常调用** ——
巡检跑在独立线程里，网关转发请求不受影响。

同时，同一时刻只允许一轮巡检。手动点「立即巡检」与后台定时轮次撞在一起时，
后来的一方会被直接拒绝并提示已有巡检在进行，避免双倍消耗上游额度、
也避免两轮各自读到的配置互相覆盖。

## 六、管理接口

| 接口 | 说明 |
| :--- | :--- |
| `GET /model-health/config` | 读取巡检配置、可选账号与上次运行状态 |
| `PUT /model-health/config` | 更新巡检配置（只覆盖显式给出的字段） |
| `GET /model-health/status` | 运行状态与当前禁用总数 |
| `POST /model-health/run` | 立即执行一轮巡检（不改变开关状态） |

巡检配置持久化在 `/data/.wb-switch/model_health_config.json`，与账号数据、账号池配置相互独立。
配置缺失或损坏时回退为「默认关闭」，**不会影响正常调用**。

## 不改变的行为

账号管理、自动签到、账号池调度（并行轮询 / 手动首选 / 请求级指定账号）、
Token 统计、既有模型别名路由，以及 v0.4.1 的模型标签手动禁用 —— **全部保持不变**。

巡检默认**关闭**，升级后保持升级前的手动禁用状态；本次新增的是「可以让网关替你自动切换
这些标签」的能力，且默认不启用。
