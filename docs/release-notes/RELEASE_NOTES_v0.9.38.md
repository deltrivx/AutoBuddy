## 背景

v0.9.37 落地了三项能力：请求级指标、成长任务等待计分落定后补领奖、配置热冷边界标注。其中**补领没有测试覆盖**（只有请求指标的 13 项测试）。

本版补上 `_test_wait_claim.py`（18 项），把补领的五条契约锁住。

## 一点自我纠正

此前我在汇报中说过「补领已实测生效（补领 13 项）」。这是**错误说法**：那 13 项是请求指标测试 `_test_reqlog.py` 的通过数，不是补领实际领到的任务数。

实际核实：我触发的 job 仍在 `running`（92%），补领设计在 vendor 子进程 `rc == 0` **之后**才运行，当时未到该阶段，日志里补领条数为 0（属预期内，但不等于"已生效"）。

## 新增测试：`_test_wait_claim.py`（18 项）

锁定的五条契约：

1. **函数存在并接线到 `_execute` 的 `rc == 0` 之后** —— 脚本成功退出才补领，失败分支不补领；
2. **只处理脚本退出时仍为 `accepted` / `in_progress` 的任务码**，达标判定为 `completed` / `claimed`；领过的移出待办，**不会重复领**，全部达标即提前结束；
3. **轮询上限 5 轮 × 2s**（整体约 10 秒，绝不拖长任务）；
4. **AT 来源优先级** —— 优先读 vendor 运行期 refresh 写回的 `wb_refresh_tokens.json`，读不到才回退旧 AT（旧 AT 会 401）；
5. **任何异常都不影响主流程** —— 只记日志，返回已领数；缺少 httpx 时跳过而非崩溃。

外加一组**等价算法验证**（不重复领、全部达标即停、已 claimed 的不重复领）。

### 为什么用源码解析而不是 import

`wb_daily` 依赖 `uvicorn`，本地 / CI 未必装了（实测 `ModuleNotFoundError: No module named 'uvicorn'`）。故沿用项目 `_test_log_dedup.py` 的既有做法：解析源码文本校验实现要点。
