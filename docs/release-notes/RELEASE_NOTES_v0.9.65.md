> 修复配额仲裁的一个边界缺陷：最优候选为 0 承接时，任何有记录的账号都会被判让位，会话连续性名存实亡。

## 背景

v0.9.64 上线后，我在容器内做功能自测时发现：A 账号被选 1 次、B 账号 0 次，
仲裁就判 A 让位 —— 这意味着几乎每次请求都会解绑去找「最近最少承接」的账号。

## 根因

原判定只有一个倍数条件：

```python
return mine_ratio > best_ratio * STICKY_QUOTA_FACTOR
```

当最优候选 `best_ratio` 为 0（新账号、或长时间未被选中）时，
阈值退化成 `> 0` —— **任何有承接记录的账号都会触发让位**。

后果不是「多让位」这么温和：会话粘性被完全架空，`select_account` 每次都走到
配额排序，用户视角就是「同一对话频繁换账号」。

## 修复

增加**绝对下限** `AB_STICKY_QUOTA_MIN_GAP`（默认 1.0），两个条件是 AND：

```python
if (mine_ratio - best_ratio) <= STICKY_QUOTA_MIN_GAP:
    return False
return mine_ratio > best_ratio * STICKY_QUOTA_FACTOR
```

⇒ 至少多出 `MIN_GAP` 次**有效承接**，才值得打断会话连续性。
⇒ 一次请求的差距不触发；明显失衡（如 10 vs 0、3 vs 1）仍正常让位。

## 测试

`_test_sched_decay_retryafter.py` 新增 [7] 组共 7 项边界用例（总数 38 → 49）：

- 最优为 0 + 仅 1 次承接 → **不让位**（本次修复的核心场景）
- 最优为 0 + 严重失衡（10 vs 0）→ 让位
- 完全持平 / 倍数失衡但差距不足 / 绑定方已是最优 → 均不让位
- 差距够但倍数不足 / 倍数与差距都够 → 让位

另锁 5 项源码契约：`STICKY_QUOTA_MIN_GAP` 常量、默认值、
`<=` 严格大于语义、与倍数阈值 AND 组合。

全量 **37 个测试文件全绿**。

## 新增可调参数

| 变量 | 默认 | 作用 |
|---|---|---|
| `AB_STICKY_QUOTA_MIN_GAP` | 1.0 | 让位的最小绝对差距（次） |
