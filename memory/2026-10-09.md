## v0.9.39：补登记（推翻上一节的「不可完成」判断）

⚠️ **上一节「任务本身不可自动完成」的结论是错的，已实证推翻。**

账号 `15828020689`（当时 1/18）在任务结束后直连上游实测：

| 查验 | 结果 |
|---|---|
| `GET /buddy/visible` | `has_buddy = true`（实例其实已存在） |
| `first_buddy` 任务 | `accept_status = claimed`，进度 1/1 |
| 对 7 个被拒任务逐个 accept | **7/7 返回 200 accepted**，回读全部 accepted |

⇒ 拒绝是**时序问题**（登记那一瞬前置尚未满足），不是任务不可完成。vendor 一拒就永久放弃，任务永远卡在 not_accepted，每轮重跑被同一理由拒掉——这才是 1/18 的真因。

新增 `_retry_accept_pending()`（在补领**之前**跑），把所有 not_accepted 重新登记。分工：

| 阶段 | 转换 | 解决 |
|---|---|---|
| ① 补登记（v0.9.39） | not_accepted → accept | 前置未满足导致登记失败 |
| ② 补领（v0.9.37） | accepted/in_progress → claim | 异步计分延迟导致漏领 |

实测成效：账号 `15828020689` **1/18 → 12/18**（job `76e4ea0959b9`，v0.9.39）。

### 踩坑（重要）

诊断脚本里把 Authorization 写成了 `"***" + at` 而非 `"Bearer " + at`，结果 16 个账号全 401、返回 HTML，脚本却打印「not_accepted 总数: 0」——**差点把这个无效 0 当成「补登记无需执行」的证据**。
教训：诊断类脚本遇到非 JSON 响应必须打印原始响应体后再判结论；**不能把「查询全失败」静默当成「结果是 0」**。生产代码 3 处 Authorization 经核实均为 `"Bearer " + at`（无 `***`），未受影响。

### 为何本轮补登记日志 0 行

实测 job 完成后全账号 `not_accepted = 0`（16/16 账号查询成功），即**无对象可做**，不打日志是正确行为——因为此前诊断脚本已把那 7 项手动 accept 成功了。补登记的实际成效体现在下一轮起：登记成功后由脚本执行上报动作。

## v0.9.40：修复「近7日/本月消耗比今日消耗还低」

用户报告：积分面板累计消耗小于单日消耗。这在数学上不可能——今日窗口必然包含在近7日/本月窗口内。

线上实测 `/api/credits/stats`：

| 字段 | 顶层 summary（全量 20 账号） | officialUsage.summary（前端实际采用） |
|---|---|---|
| usageToday | 5280.01 | 5280.01 |
| usage7Days | 19573.14 | **3597.49** ❌ |
| usageThisMonth | 21435.50 | **3819.01** ❌ |

根因：`officialUsage` 这条采集通道只覆盖 **6 个账号**，顶层是全量 **20 个账号**，合计类字段天然偏小；官方前端优先采用 `officialUsage`（`status=complete` 即视为可用），把全量累计值覆盖成残缺值。

**这是我 2026-10-08 修复「今日消耗一直是 0」时留下的半截尾巴**：当时只对了 `usageToday`，并在注释里假设「usage7Days / usageThisMonth 官方是有值的」。实测证明该假设不成立。

修复：把 `usage7Days` / `usageThisMonth` 一并纳入「以顶层为准」的对账；再加单调护栏，保证「近7日 >= 今日」且「本月 >= 今日」。刻意**不**断言「本月 >= 近7日」——月初前几天本月窗口可能短于 7 天，那样断言会造出新的错误。

实测生效：三者均为 5280.01 / 19573.14 / 21435.5，单调校验 True。

### 教训（已写进代码注释）

给外部数据源做对账时，**「部分字段准」不等于「其余字段也准」**。凡是被子集覆盖的通道，它的**合计类**字段一律不可信，必须逐个字段验证——不能因为一个字段对上了就假定其他字段也对。
