> 修复积分统计漏 15 个账号、token 统计只显示 2 天；429 盲目退避改为按上游重置墙钟冷却。

## 起因

参照 `linguo2625469/workbuddy2api-panel`（2009★）做了一轮能力对比，并对
「积分统计异常」和「token 消耗异常」做了实证诊断，查出三个真实缺陷。

## 修复内容

### 一、积分统计漏掉 15 个账号

**实测现象**：上游 `/api/credits/stats` 返回 **34 个账号**，经代理过滤后只剩 **5 个**。

**根因** —— `gateway/web_proxy.py` 的过滤逻辑取到第一个非空列表就 `break`：

```python
for acc_file in [AB_DATA_DIR/"accounts.json", "/data/.wb-switch/accounts.json"]:
    ...
    if valid_account_ids:
        break
```

而实测两份文件：

| 文件 | 账号数 |
| :--- | --- |
| `/data/.autobuddy/accounts.json` | 5 个 |
| `/data/.wb-switch/accounts.json` | **20 个**（完整） |

并且 5 个是 20 个的**子集**（交集 5、仅后者有 15），于是用了不完整的那份做过滤。

**佐证矛盾**：summary 里 `todayCheckedInAccounts=15` —— 那 15 个账号正在签到，
却不在账号列表里。

**修复**：两个来源取**并集**，谁都不漏。

### 二、token 统计只显示 2 天（数据其实有 8 天）

**实测现象**：SQLite 里明明有 8 天、15663 条记录，但 `/api/token-stats` 只返回 2 天。

**根因**：`MAX_DETAIL`（3000）本是 **JSON 模式写入侧**的文件体积护栏，却被借来做
**SQLite 读取侧**的 `LIMIT`。本网关实测每天约 1900 条调用 —— 3000 的 LIMIT 只够
覆盖约 1.5 天，于是 v0.9.28 定的「7 天时间保留」策略**形同虚设**。

**实证**：

```
limit=  3000: 取回  3000 条, 覆盖 2 天 -> ['2026-10-07', '2026-10-08']
limit= 50000: 取回 15666 条, 覆盖 8 天 -> ['2026-10-01' ... '2026-10-08']
```

**修复**：新增 `DETAIL_READ_LIMIT`（默认 200000）专管读取侧。职责分开：

- 时间跨度 → `DETAIL_MAX_DAYS`
- 读取上限 → `DETAIL_READ_LIMIT`（新）
- 写入侧文件护栏 → `MAX_DETAIL`（仅 JSON 模式）

### 三、429 盲目指数退避 → 按上游重置墙钟冷却

参照 workbuddy2api-panel 的做法：上游 429 `code=6004`（**模型级**限流）明确带
重置时间，例如：

```
您的使用量已超出频率限制，将在 2026-10-08 10:39:26 UTC+8 重置，
您也可以切换其他模型继续使用。
```

**退避是猜，重置时间是上游明确承诺的解封点。** 退避过短会白撞几次，过长又浪费可用额度。

现在解析出重置墙钟并采纳，**且只在它比退避更晚时才用** —— 避免上游给了一个过去的时间戳反而缩短冷却（那样会白撞）。解析不出时回退到指数退避，宁可保守，也不错冷却。

## 为什么这三个都是"真实缺陷"而非猜测

| 缺陷 | 实证依据 |
| :--- | --- |
| 积分漏账号 | 上游 34 → 过滤后 5，而 summary 显示 15 个在签到 |
| token 只 2 天 | `limit=3000` → 2 天；`limit=50000` → 8 天，数据都在库里 |
| 429 退避 | 上游文案稳定携带 `将在 YYYY-MM-DD HH:MM:SS UTC+8 重置`，可被稳定解析（3/3 命中） |

## 关于「补全整体功能」的说明

本次只做**已实证确认的缺陷修复**，不批量照搬参考项目功能 —— 那是更大的工程，应等你确认优先级后再动。

对照参考项目后仍未实施、但已识别的差距（供你定夺）：

- **成长任务一键完成 17/18**：参考项目可用纯 API 自动推进并领奖，而我们依赖 vendor 脚本，且历史上有 `first_buddy task not completed yet` 未闭环的已知问题。
- **在线配置热生效**：参考项目改 `config.json` 立即生效；我们多数配置需重建容器才生效。
- **请求指标面板**（成功率 / 平均耗时 / 最近请求 + `X-Request-Id`）：我们只有用量聚合，没有请求级可观测。

另外，实测发现仓内 vendor 已有官方 UA，但聊天转发路径此前未使用（v0.9.35 已修）。
