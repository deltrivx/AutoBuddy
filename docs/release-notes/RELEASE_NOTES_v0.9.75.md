> 主动播报落地：任务失败时推送**智能分析**（原因 + 建议），与既有通知分工不重叠。

## 需求

三阶段路线（阶段 4 查询全覆盖 → 阶段 5 写操作确认 → 阶段 6 主动智能）交付后，
用户确认要做方案里的第三项「主动播报」。

## 分工原则（关键设计）

既有 7 个通知场景中，`task_done` 已经发「任务完成 + 积分」。如果失败时再发一条
内容雷同的通知，用户会被重复信息骚扰。

因此本次严格分工：

| 场景 | 发什么 | 示例 |
|---|---|---|
| `task_done` | **事实** | 本次任务积分、参与账号数 |
| `task_failed_analysis`（新增） | **分析** | 为什么失败、该怎么办、进度、已运行时长 |

两者内容不重叠，同一事件不会重复推送。

## 实现

1. **`notify.build_task_failed_analysis()`** —— 把失败 detail 翻译成
   「原因 + 建议 + 进度 + 已运行时长」；
2. **`notify._classify_task_failure()`** —— 共享归因映射，助手工具
   `diagnose_task_failure` 也调它。这样「问助手」和「主动推送」**口径一致**，
   不会出现两套说法；
3. **`wb_daily._notify_task_failed()`** —— 两处失败出口都接：
   - `rc != 0` 分支（脚本真失败）
   - `_guard` 兜底（异常/未知退出，`_execute` 没覆盖到的出口）
   - `_failed_notified` 幂等标记保证**一轮只发一次**；
4. 推送放在 `_persist_run()` **之后** —— 确保落库完成再推，面板与推送数据一致；
5. 通知异常一律吞掉 —— 附属功能绝不能影响任务主流程。

## 归因映射（确定性，不猜）

| 失败 detail | 归因 | 建议 |
|---|---|---|
| 进程中断（容器重启/被终止） | 进程被中断 | 多为发版重建容器所致，非系统缺陷 |
| 无可用账号 | 账号池无可用账号 | 检查凭据过期 / 账号被全部停用 |
| 执行超时 | 执行超时 | 账号多时属正常，可提高单账号超时 |
| 内置脚本缺失 | 内置脚本缺失 | 镜像可能不完整，建议重建容器 |
| 其他 | 原文截断 | 查看容器日志进一步定位 |

## 实测文案

```
🔍 每日任务失败分析
  · 原因：进程被中断（容器重启/被终止）
  · 建议：多为发版重建容器所致，非系统缺陷；避免在执行中重建容器
  · 进度：账号 18/22
  · 已运行：45 分钟
```
