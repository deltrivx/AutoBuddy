> 阶段 5：写操作两段式确认 —— 写操作永不被自然语言直接触发，必须先经一次显式确认。

## 动因（用户原话）

> 「我只是问他今天执行过任务吗？为何就直接执行了……交互是交互，
> 智能助手是智能助手，可以包含交互菜单命令，而不是交互菜单不够了才调用智能助手。」

v0.9.71 修掉了「疑问句被命令拦截」；本阶段解决另一半：
**写操作永不被自然语言直接触发**。

## 设计：结构性防线，不靠提示词

```
用户: 执行任务
助手: 【待确认】将启动一轮每日任务（签到 + 成长任务 + 领奖）
      · 影响：全部参与账号（通常 20+ 个）
      · 预计：约 40-60 分钟
      · 回复「确认」执行，「取消」放弃（300 秒内有效）
用户: 确认
助手: ✅ 已启动一轮每日任务（job_id: xxxx），完成后会自动推送结果
```

1. **意图识别是确定性的**：关键词表 + 精确匹配，**不经过 LLM**；
2. **双保险**：`_write_intent` 内先调 `_looks_like_question`，疑问句永远不进写意图；
3. **影响预告**：每个写操作带 `impact`（影响范围）+ `estimate`（耗时预估），
   确认前可见 —— 用户知道会发生什么才按确认；
4. **确认态 TTL 5 分钟**（短于对话 30 分钟，确认是即时决策）；
5. **审计日志**：每次实际执行记录时间/会话/操作/参数/结果，可事后追溯。

## 6 个写操作

| action | 说明 |
|---|---|
| `run_daily` | 启动一轮每日任务 |
| `checkin_all` | 全部账号签到 |
| `abort_daily` | 中止当前运行的任务 |
| `probe_models` | 立即执行一轮模型巡检 |
| `notify_on` / `notify_off` | 通知推送总开关 |

**有意排除**（面板可做，助手不做）：登录/改密、导入导出、删除全部 Key、
账号永久删除 —— 涉及凭据与数据主权。

## 过程中修掉的一个真 bug

修完发现 `run` 命令**绕过**了确认流程直接执行（实测 `fired=[RUN]`）。

根因：`_EN2ZH` 把 `run` 归一成「任务」，于是它不再匹配
`_write_intent` 的 `run` 分支，而是落到旧写操作分支立即执行。

修正：`run` 不再归一（保持原形即可被识别为 `run_daily`，先进确认流程）；
`daily` 仍归一为「任务」——它是只读查询（进度），走查询分支。

## 验证

完整流程线上实测通过：

```
[下令] → 【待确认】+ 影响 + 预计 + 确认/取消指引
        running 任务数: 0  ✅ 未执行
[取消] → 已取消，未执行任何操作。  待确认已清除
[确认] → ✅ 已启动一轮每日任务（job_id: 1edf6acdb671）
        审计日志: 19:32:01 | run_daily | ok=True | ...
```
