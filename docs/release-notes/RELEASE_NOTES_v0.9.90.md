## 一、日报两个数据 bug

你收到的那份日报：

```
💰 积分五项
  · 昨日签到积分：0          ← 实际 2,200
  · 昨日任务积分：400
  · 昨日总积分：400          ← 实际 2,600
  · 昨日消耗积分：2,787.8
🔌 API 调用
  · 昨日调用：0 次           ← 实际 3,691
```

### 1. 「昨日签到积分」恒为 0

**根因**：日报和页面走的是**两条不同的取数路径**。

| 路径 | 数据来源 | 签到积分 |
| :--- | :--- | :--- |
| 页面（积分统计页） | HTTP 层 `_merge_checkin_credits()` | ✅ 有 |
| 日报 | 直接读 `db.summarize_wb_daily_credits()` | ❌ 恒 0 |

`summarize_wb_daily_credits()` 只从 `wb_daily_tasks` 的 detail 文本里正则抠「+N积分」，而 checkin 行的 detail 恒是这句话：

```
✅签到: 今天已签到，请明天再来（签到连签5天，累计500）
```

**一个数字都没有**。所以签到奖励在这个函数里永远是 0。

页面没这个问题，是因为 HTTP 层额外跑了一遍 `_merge_checkin_credits()`，用账号签到状态里的 `raw.daily_credit` + `raw.checkin_dates` 把签到积分补回去。

**修复**：日报复用同一套合并逻辑，不再绕过它。

实测修复前后：

```
昨日签到积分：0      → 2,200
昨日总积分  ：400    → 2,600
累计任务积分：41,600 → 68,900
```

### 2. 「昨日调用」翻倍

`token-stats` 返回两个 source：`workbuddy` 和 `workbuddy-ai`。原代码把它们同一天的 `records` **直接相加**，但这两个 source 扫的是**同一批文件**：

| 对比项 | workbuddy | workbuddy-ai |
| :--- | :--- | :--- |
| filesScanned | 20,434 | 21,034 |
| projects | 6 个手机号 | 完全相同 |
| models | 6 个模型 | 完全相同 |
| daily | 10-10 起 | 多含 9-22/9-23 两天 |

于是 10-16 的调用数被报成 **7382**，实际 **3691**。

**修复**：改为取「每个日期在所有 source 中的**最大值**」。同一批文件的重复来源取 max 即真实值；真有两个独立来源时 max 也不会把小的漏掉。

### 3. 「轮检禁用：376」看不懂

376 不是「376 个模型被禁用」，而是「账号 × 模型」的**组合数**——21 个启用账号 × 约 19 个被轮检判禁用的模型。日报里裸报一个组合数，用户完全没法理解它是什么、该不该管。

改为「376 个账号×模型组合」。

## 二、签到通知重复推送

**现象**：签到配了 24 小时一次，却短时间内连收两条，还违背「重复消息不推送」原则。

**根因**：`_notify_checkin_once()` 挂在「账号完成处」，**完全不看轮次类型**。而任务轮会被巡检 / 调度 / 手动执行反复拉起，于是签到通知也跟着一轮接一条。

实测最近 20 轮执行记录里，**20 轮全是 `task` 轮，0 轮 `checkin` 轮**——也就是说签到通知全是被任务轮顺手发出来的。

**修复**：两道防线。

1. **只有签到轮才发**：任务轮的职责是「签到以外的全部任务」，本来就不该由它报告签到结果。
2. **跨轮次时间窗**：轮内幂等标记只能保证「这一轮只发一条」，但签到轮自身也可能被巡检短时间反复拉起（中断 → 恢复 → 再中断）。新增 6 小时最小发送间隔，时间戳**落库**（跨进程、跨重启有效），不依赖内存标记。

> 只有真的发出去了才记时间戳。被内容去重（deduped）不算一次有效推送 —— 否则两条相同内容会互相压制，后续真的变化也发不出来。

## 三、中断任务的明细不再全丢

**现象**：任务跑到 92%（7/22 账号）被强杀，DB 里这一轮的逐账号明细是 **0 行**。

**根因**：`_persist_run()` 原先只在任务**结束**时调一次。而 SIGKILL / 容器重建时，`_guard` 的 finally 都没机会跑 —— 于是中断轮次的明细全部丢失。

后果是**断点续跑永远无账可续**：`_already_done_accounts()` 取不到已完成的账号，只能整轮 22 个账号重跑。实测 6 个中断轮次 `accounts=0`、`wb_daily_accounts` 零行。

**修复**：任务执行期间每 **20 秒**增量落盘一次。

- 面板能实时看到「这一轮已经跑完哪几个账号」
- 被强杀时最后几十秒的进度已在库里，续跑能真正跳过已完成账号
- `save_wb_daily_run` 用 `INSERT OR REPLACE`，同一 job_id 重复落盘是设计内的

## 四、API 密钥按维度统计

### 之前

每个密钥只有一行 badge：「调用 45,555 次」。

### 现在

每个密钥行下方多出一行统计：

```
Default | 今日调用=5 次  累计调用=5 次  今日词元=1.25M  累计词元=1.25M  输入/输出=1.25M / 2.1K
iMohican | 暂无调用明细（该密钥还未被使用，或使用时间早于统计启用）
```

### 实现链路

```
/v1/chat/completions
  → _gateway_auth() 解析出 keyId / keyName
  → record_token_usage(..., key_id=..., key_name=...)
  → token_store.insert_batch() 写入 usage_logs.key_id / key_name
  → get_aggregated_token_stats() 新增 byKey 聚合
  → /api/token-stats 返回
  → 设置页「API 接入」渲染统计子行
```

`usage_logs` 表新增 `key_id` / `key_name` 两列，带幂等迁移（复用既有的 `_ensure_column` 机制，老库自动补列）。

**取不到数据时显示「暂无调用明细」而非编造 0** —— 「没有记录」和「真的是 0」是两件事。

> 历史记录没有 keyId（记账是这次才加的），所以老密钥会显示「暂无调用明细」，等新的调用进来后自动出现数据。
