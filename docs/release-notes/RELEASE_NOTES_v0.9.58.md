## ① 修复「点击执行却没有记录」（用户 2026-10-13 报告）

实测 job `29302d1e93a8`：跑了 30 分钟后日志末尾是「执行超时（30 分钟），已强制终止」，
状态 `failed`，但 `wb_daily_runs` 表里**没有这条记录**、`wb_daily_tasks` 落库 0 条。

根因：`_execute` 的**超时分支**和**手动中止分支**在 `return` / `raise` 前都没有调
`_persist_run()`——只有 `rc == 0` / `rc != 0` / `rc < 0` 三条正常路径落了库。
于是被强杀/中止的这轮在面板「执行记录」里完全看不到。

修复：超时与中止分支都补 `_persist_run(job, all_lines)`，四种终态全部留痕。

> 附带说明：超时本身是因为账号池涨到 22 个、单轮耗时超过 30 分钟上限。
> 这是容量问题而非缺陷——本轮已让它留痕，是否要放宽 `WB_DAILY_TIMEOUT` 需你定。

## ② 调度算法：配额制（此前未按预期工作）

用户要求「积分多的优先多调用、积分下来了让位给别的账号」。实测初版实现
**没生效**：余额-承接次数相关系数仅 0.077（应为明显正相关）。

演进（实测数据说话）：

| 版本 | 算法 | 实测 |
|---|---|---|
| v0.9.44 | 纯 inflight 最少连接 | 不感知余额，相关性 -0.137 |
| v0.9.45 | `inflight / weight` | 相关性 0.077——inflight 主导，权重形同虚设 |
| **本版** | **配额制**：已选次数 / 配额比例 最小者优先 | 3:1 余额 → **75% : 25%** |

配额 ∝ 余额（封顶 8 倍防单号打爆），**自纠**：某号选多了比值升高、自动让位。
未知余额（快照缺失/新账号）→ 中性权重，不被饿死。`AB_CREDIT_WEIGHT=0` 可关闭。

算法经模拟验证六组场景：3:1 分摊、衰减后反超、同余额 1:1、未知余额中性、
无数据退回 inflight、极端差额仍保底下限。
