## 一、修复：账号卡片的排版会漂

同一个账号页里，每张卡片的内容块顺序并不总是一样 —— 具体表现是「近期到期 / 积分明细」
有时在卡片中间，有时掉到卡片最底；「账号池控制条」与「可用模型」的先后也会互换。

| 卡片内的顺序 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 积分摘要 → 近期到期 / 积分明细 → 账号池控制条 → 可用模型 | 常有卡片不是这个顺序 | 每张卡片都一致 |

**为什么会漂**：卡片里有两部分内容，官方自己的积分信息，以及容器注入的「账号池控制条 + 可用模型」。
它们由**各自独立的异步流程**写进同一个容器：

- 官方的积分明细要等数据回来才渲染，追加时按「自己是最后一个」处理，于是落到注入的两块**之后** ——
  看起来就成了「明细掉到卡片最底」；
- 注入的两块各走一个请求，**先回来的先插入** —— 于是控制条与可用模型的先后也会互换。

**怎么修的**：每次渲染后按固定顺序把注入的两块挪回卡片末尾，官方内容一律排在它们之前。
已经是目标顺序时不做任何动作，所以不会来回抖动。

> 卡片里的数据与按钮功能都没有改动，只是位置不再变化。

## 二、新增：账号卡片顺序的构建期检查

注入脚本的排版问题以往只能靠肉眼发现。这一版把它纳入构建流水线：复现「官方晚一步追加明细」
这一情形，断言两块仍被拉回末尾，同时校验只有官方内容的卡片不会被误动。

## 不改变的行为

账号管理、自动签到、账号池调度（并行轮询 / 手动首选 / 请求级指定账号）、模型别名路由、
模型标签的手动禁用、模型可用性巡检的开关与判定规则 —— **全部保持不变**。

对外提供的 OpenAI 兼容接口、请求与响应字段**没有任何增删**。
