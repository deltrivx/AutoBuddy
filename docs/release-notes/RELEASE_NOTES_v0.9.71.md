> 修复「问一句就跑一轮任务」：疑问句被交互菜单的子串匹配拦截并触发写操作。

## 用户反馈

> 我只是问他今天执行过任务吗？为何就直接执行了，是被交互菜单拦截了吗？
> 交互是交互，智能助手是智能助手，可以包含交互菜单命令，
> 而不是交互菜单不够了才调用智能助手

## 实测根因

复现 5 种问法，**全部命中写操作**：

```
今天执行过任务吗  -> _cmd_run()   ← 用户遇到的
任务跑完了吗      -> _cmd_run()
任务进度          -> _cmd_run()
执行任务          -> _cmd_run()（这条本就该执行）
任务              -> _cmd_run()
```

根因：`if "任务" in text` 是**子串匹配**，根本分不清「问状态」与「下令执行」。
用户问一句「今天执行过任务吗」，网关就直接把 22 个账号的每日任务跑了一遍。

## 用户指出的设计缺陷（已采纳）

> 「交互是交互，智能助手是智能助手，可以包含交互菜单命令，
> 而不是交互菜单不够了才调用智能助手。」

即：菜单与助手应**平级**，助手不是「命令没命中时的兜底」。

## 修复

1. **疑问句优先交助手**：新增 `_looks_like_question()`（吗/呢/什么/多少/哪些/
   怎么/怎样/如何/是否/是不是/有没有/能否/能不能/可不可以/？/?/跑完/跑过/执行过/跑了），
   作为**一等公民入口**放在命令分支**之前** —— 助手能用只读工具回答的，
   绝不被命令分支拦截；
2. **写操作只认显式精确命令**：`执行任务`/`启动任务`/`跑任务`/`运行任务`/`run`、
   `签到`/`全部签到`/`checkin`，且先剥首尾标点再精确匹配；
3. **只读查询仍允许关键词命中**（误命中也只是多返回数据，无害）；
4. **助手不可用时降级到只读兜底** `_readonly_fallback()`：只走查询命令，
   红线是**绝不调用写操作** —— 疑问句永远是查询，助手挂了也不能把用户的任务执行了；
5. 顺带修 `_tool_task`：原先只读内存态 `jobs`（容器重启即丢），
   「今天跑过吗」无从判断。现补 `runs`（SQLite 落库）并统计今日轮次与成败。
