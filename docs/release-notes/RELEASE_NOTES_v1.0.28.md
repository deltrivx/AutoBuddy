修积分统计页误报「部分账号官方用量未同步」——账号状态字段改为如实反映，与 `errors` 数组自洽。

## 一、现象

积分统计页长期同时显示两件互相矛盾的事：

- 顶部提示「已同步 **4/4** 个当前账号」
- 却又警告「**部分账号**官方用量未同步」
- 失败账号的官方数值一栏全是「—」

实际 4 个当前账号全部同步成功。这是**误报警告**。

## 二、根因

`gateway/web_proxy.py` 的 `_reconcile_official_usage()` 负责把官方采集停更后的
`officialUsage` 全量接管为网关实时口径。它在重建 `ou.accounts[]` 时，把每个账号的
状态字段**无条件硬编码**：

```python
rebuilt.append({
    ...
    "detailTruncated": True,      # 宣称「明细被截断」
    "error": None,                # 宣称「无错误」
    "ok": True,                   # 宣称「同步成功」
    ...
})
```

紧接着又无条件清空错误列表：

```python
ou["errors"] = []
```

**这四个字段自相矛盾**：`detailTruncated=True` 说「明细被截断」，`errors=[]` 却说
「没有任何错误」，`ok=True` 又说「全部同步成功」。

官方前端读到 `detailTruncated=True` 就判定「有账号未同步」，于是弹出警告；而它统计
`ok == true` 的数量时又得到 4/4。两边用了互相冲突的字段，造出了这个荒谬的组合提示。

## 三、修法

状态字段改为**如实反映真实数据**，不再硬编码：

| 字段 | 旧值（硬编码） | 新值（如实） |
| :--- | :--- | :--- |
| `detailTruncated` | 恒 `True` | 仅当该账号真的没有逐模型明细时为 `True` |
| `ok` | 恒 `True` | 取决于该账号是否取到 daily 数据 |
| `error` | 恒 `None` | 仅当真的没明细时给出可读文案 |
| `errors[]` | 恒 `[]` | 由 `accounts` 里 `ok=False` 的项聚合而来 |

核心判定变量：

```python
_acc_has_detail = bool(_new_daily) and bool(_acc_models)
```

于是：

- 4 个账号全部有明细 → 全部 `ok=True` → `errors=[]` → **不误报**
- 真的某账号没明细 → 该账号 `ok=False` + `error` 有文案 + 出现在 `errors[]` → **如实报**

`errors` 的聚合规则保证它永远与 `accounts` 严格自洽，不会再出现「明细被截断却无错误」
这种内部矛盾。

## 四、影响范围

| 项 | 说明 |
| :--- | :--- |
| 改动量 | `+26/-4` 行，只改状态字段的取值来源 |
| 业务逻辑 | **零改动**。usageToday / usage7Days / usageThisMonth 校准、账号明细接管、图表三件套接管全部保持原样 |
| 数据口径 | 不变。数值仍来自网关实时快照 |
| 用户可见变化 | 「部分账号官方用量未同步」警告只在**真的**有账号未同步时才出现 |

## 五、验证

新增 `tests/test_official_usage_sync_status.py`，23 项断言，锁定自洽性契约：

- 状态字段不得硬编码（缺陷根因）
- 状态由真实数据决定
- `errors` 数组与 `accounts` 自洽
- **全同步时不得误报**（用户缺陷的核心断言，含可执行样本验证）
- 未破坏既有校准逻辑

反向验证：用修复前的旧源码跑同一测试，13 项 FAIL；修复后 23 项全过。证明该测试
确实能捕获此缺陷，不是空转的门禁。
