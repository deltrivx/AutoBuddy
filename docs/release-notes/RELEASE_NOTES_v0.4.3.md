## 需求

v0.4.2 引入了模型可用性巡检：定期探测每个账号的每个模型，调不通的自动禁用、恢复的自动启用。
自动化方向是对的，但这一版实测下来有两处必须修：

1. **探测把「模型不可用」判错了** —— 一轮巡检下来，所有组合都被判成不可用，
   用户的禁用清单从 46 项膨胀到 231 项，好模型被成批误禁；
2. **自动启用会抹掉人为的禁用决定** —— 它无法区分「别人关的」和「我关的」，
   于是「能跑但太贵，别用」这类主动取舍会被自愈悄悄放开。

v0.4.3 修掉这两点，并给设置页补上最后一块「关于」。

---

## 一、修复：探测请求的形态与真实调用不一致

**症状**：开启巡检后跑一轮，结果是「探测 200 个组合，可用 0、不可用 200」——
一个可用的都没有。这在真实使用中不可能发生（网关当时是正常工作的），
说明问题出在探测本身，而不是模型。

**原因**：探测是**直接发往上游**的（只有绕开网关自己的路由，才能精确测出「某个账号的某个模型」
通不通），但探测请求的形态没有对齐真实调用：

| 上游的硬性要求 | 真实调用 | 探测（错误） |
| :--- | :--- | :--- |
| 只接受流式请求，非流式直接拒绝 | 自动改写为流式 | 发的是非流式 → **被拒** |
| 首条消息必须是系统提示词 | 自动补齐 | 直接以用户消息开头 → **被拒** |

两条都不满足，于是每一次探测都被上游以请求参数错误回绝。
判定逻辑把它读成「这个模型不可用」，进而成批写入禁用。

**修复**：探测请求补齐了流式与首条为系统提示词这两处形态。
同一批模型复测：可用的正常返回 200，真正不存在的模型返回明确的「模型服务不存在」，
两者能被区分开。请求参数层面还剩一处差异，由 v0.4.4 一并去掉。

## 二、新增：整轮误判保护

修掉根因还不够 —— 这类缺陷的**后果**太重：它不会报错，只会安静地把配置改坏，
而用户往往过很久才发现。

因此新增一道防线：**一整轮里如果没有任何一个组合可用，且不可用的数量达到了门槛，
就判定为探测机制本身出了问题**（凭据失效、上游整体故障、请求形态被拒），
本轮**整轮作废，不写任何配置**，并在设置页明确提示「已跳过」及原因。

理由很直接：模型不会约好了同时失效。宁可漏禁一轮，也不要误禁一批 ——
漏禁下一轮就补回来了，误禁却要靠人工逐个放开。

同时，构建流水线现在会在打包镜像**之前**跑一遍本地单测；测不过就不出镜像。
上面那个缺陷正是「单测能发现、但当时没人跑」的类型。

## 三、新增：禁用项区分「手动」与「巡检」

每个禁用项现在带一个来源标记：

| 来源 | 谁写的 | 探测到可用时会怎样 |
| :--- | :--- | :--- |
| **手动** | 你在账号卡片上点掉的 | **不动**，不会被自动放开 |
| **巡检** | 自动探测判定不可用后写入的 | 自动放开（这就是自愈） |

**为什么必须区分**：手动禁用通常不是「坏了」，而是「能用但我不想用」——
最常见的就是控成本。v0.4.2 无法区分两者：只要模型可达，自动启用就会把它移出黑名单。
实测在一份 46 项的手动禁用清单里，有 22 项实际是可达的，开启自动启用后会被静默放开，
等于把人的取舍直接作废。

现在自动启用**只会放开自己写进去的那些**。手动禁用始终由人说了算 ——
这也让「自动启用」这个开关终于可以安全打开：既能自愈，又不会碰你的配置。

> **升级兼容**：旧版本的禁用清单在读取时**一律视为手动禁用**。
> 之前没有巡检，清单全部来自人工点击，这个归属是准确的 ——
> 升级不会因为「来源未知」而把你的旧配置当成可自愈的项放开。

## 四、设置页：账号卡片能看出「是谁关的」

两种禁用态在卡片上可一眼区分：

- **手动禁用**：灰色删除线，悬停提示「巡检不会自动放开手动禁用的模型」；
- **巡检禁用**：琥珀色删除线，悬停提示「模型恢复后会自动启用」。

卡片标题上的徽章也从单一的「已禁用 N」拆成两枚：原来的总数，以及单独标出的「巡检 N」。

巡检面板里则新增一行**当前禁用构成**：手动禁用多少项、巡检禁用多少项。

## 五、设置页：关于

设置页最底部新增「关于」区块，回答「我装的到底是什么」：

- 项目名称与当前版本，以及**项目主页 / 更新日志 / 发布版本 / 问题反馈**入口；
- **容器镜像地址**，可一键复制；
- **数据目录与端口**，并注明升级不会动这个目录里的账号与配置；
- **当前规模**：账号数（可用 / 参与调用）、模型数、禁用组合数（按来源拆分）；
- 非官方项目声明。

其中项目地址与镜像名由服务端下发，可用环境变量覆盖 —— 二次分发的版本不会把使用者引回本仓库。

## 六、其他修复

- **点「立即巡检」后界面不刷新**：巡检结束后的刷新调用指向了一个不存在的函数，
  报错被静默吞掉，导致跑完一轮后面板与账号卡片仍显示旧状态。
- **巡检结果日志口径统一**：手动触发与定时轮次现在共用同一条结果日志，
  都会打印组合数、可用 / 不可用 / 跳过与是否作废。
- **上次巡检结果不再随重启丢失**：结果会落盘，容器重启后设置页仍能看到上一轮的统计，
  不必等到下一个巡检周期。

## 七、升级方式

```bash
docker pull ghcr.io/deltrivx/workbuddy-switch:v0.4.3
docker pull ghcr.io/deltrivx/workbuddy-switch:latest
```

> Unraid 请通过容器模板重建，**不要手工拼接 `docker run`**。
> 数据目录不变（`/data`），账号、密钥、账号池与模型策略都会原样保留。

### 如果你在 v0.4.2 期间开过巡检

请到设置页看一眼巡检面板里的**当前禁用构成**：

- 若「巡检禁用」的数量远超你实际调不通的模型数，说明被上面那个缺陷误禁过。
  这些项可以逐个在账号卡片上点回；
- 巡检在改动策略前会自动留一份备份，把它恢复为当前策略后重启容器，即可一次性回到误禁之前的状态。

升级到 v0.4.3 后，即使再出现同类异常，整轮保护也不会再让它写坏配置。

## 八、不改变的行为

账号管理、自动签到、账号池调度（并行轮询 / 手动首选 / 请求级指定账号）、Token 统计、
模型别名路由、模型标签的手动禁用，以及 v0.4.2 的巡检间隔与账号范围设置 —— **全部保持不变**。

判定分档（限流与超时一律跳过）、探测只看状态码而不解析模型输出、
同一时刻只允许一轮巡检、巡检不阻塞正常调用 —— 这些 v0.4.2 的取舍继续沿用。
