## 新增 2 个「会判断」的工具

与阶段 4 的工具不同，这两个不只是取数，而是**基于数据做判断并给建议**：

### `get_credit_trend` —— 积分趋势

- 以「近 7 天日均」为主口径估算可支撑天数（比今日单日更稳）
- 以「本月日均」作对照，两个口径差异大时提示节奏变化
- 给出**预计见底日期**，< 7 天明确预警，< 15 天提示关注
- 今日消耗显著高于近期日均时，提示可能有异常调用

线上实测：

```
积分趋势：
  · 当前剩余：40,980.82（总额度 126,531，已用 67.6%）
  · 近 7 天日均消耗：8,182.57
  · 本月日均消耗：4,805.44（已过 14 天）
  · 按近 7 天速度，约可支撑 5.0 天（预计 2026-10-19 前后见底）
  ⚠️ 不足 7 天！建议减少调用或补充账号额度。
```

### `diagnose_task_failure` —— 任务异常归因

- 从 `/api/wb-daily/runs` 的 `summary.detail`（v0.9.61 起落库的真实原因）归因
- 已知原因**确定性映射**到原因 + 建议，不猜：
  - 「进程中断（容器重启/被终止）」→ 多为发版重建容器所致，非系统缺陷
  - 「无可用账号」→ 检查凭据过期 / 账号被全部停用
  - 「超时」→ 账号多时属正常（按账号判定），可提高单账号超时

## 过程中修掉的一个真 bug（线上实测暴露）

第一版归因工具把**仍在运行**的任务报成「失败」：

```
任务异常归因（最近 20 轮中有 4 轮未成功）：
  · 9789ee6e3782（10-14 19:46，manual）
    - 原因：原因未记录        ← 误报，这轮正在跑（当时 9/22）
```

根因：过滤判据是 `status != "done"`，把 `running` / `pending` 也算成失败。

修正：只有**终态且非成功**（`failed` / `aborted`）才算失败。
修正后实测：同一份数据从「4 轮未成功」变为「3 轮未成功」，且不再出现
运行中的任务，三条失败均正确归因到「进程中断（容器重建）」。

## 关于「主动播报」

方案里的第三项（任务失败时助手主动分析并推送）**未在本版实现** ——
它需要与现有 7 个通知场景设计去重规则（避免同一事件既发通知又发助手分析），
且要在通知链路里新增一个场景。这部分留待你确认后再做，本版先把
「问得出趋势、问得出原因」落地。
